# Olist 经营分析产品设计

## 已确认目标

面向电商公司管理层，把现有驾驶舱从“模拟指标页”升级为可用完整 Olist 公开历史数据回放和分析的经营产品。产品页维持正式的经营系统表达；第三方代码、数据许可、数据源链接与学习边界仅存放在仓库内部文档和通知文件中。

## 事实数据边界

数据源固定为 Olist Brazilian E-Commerce Dataset 的九张核心表：订单、订单明细、付款、评价、客户、卖家、商品、地理位置、品类翻译。所有统计以订单购买时间和回放时刻为时间边界。

可交付的管理层内容：成交额、订单、客单价和同期对比；支付结构与分期；订单状态、下单至审批/交运/签收时长、准时与逾期；类目、商品、卖家、客户州/城市贡献；独立买家、复购与集中度；评分分布、差评和履约关联；可追溯的订单与可信分析。

不提供没有事实来源的库存、采购成本、毛利、广告花费/ROI、会话流量/转化率、退款金额、目标预算或未来预测。这些字段不作为产品页的占位卡片或伪造指标。

## 架构

`source/importer/verifier` 负责可验证导入；`repository` 是唯一的指标语义层；`route` 只暴露已校验的快照；`analysisContext` 从同一快照生成可引用事实；React Provider 只消费 API 快照。

所有模块共享同一个时间范围、筛选和回放上限。付款、履约、客户、体验、排行与订单明细必须由该语义层输出，不能在前端各自重算。

应用使用 CoreUI 外壳提供“概览、实时监控、智能分析、经营数据”四个固定入口。每次只挂载当前数据源的 Provider 与图表页，避免模拟轮询和 Olist 轮询并行。页面统一显示刷新时刻、加载、空态、错误与重试；不具备事实的模块直接不出现。

## 验收准则

1. 导入必须覆盖九张表，并校验付款复合主键、付款订单外键、地理源行数和原子回滚。
2. 语义层的所有新增指标有手算 fixture；回放、日期、类目、卖家、客户地域筛选同时生效。
3. 付款、客户、履约、评价、商品/卖家/地域模块都可追溯到同一快照，AI 回答带该快照时间且不越过可用事实。
4. 产品 UI 不出现“Demo/模拟数据/真实试点”式显眼声明；内部归属文件齐全。
5. 切换工作区会卸载非活动 Provider；导航可键盘操作；桌面和移动端无横向溢出。
6. 单元、类型、构建、Playwright、截图、敏感信息扫描与许可证检查均通过。

## 分阶段交付

第一阶段先完成数据导入与语义指标，第二阶段把真实管理模块接入 CoreUI 壳层，第三阶段做可信分析、回放和浏览器验收。每阶段独立提交和审查，确保网络或应用流中断不会丢失可验证进度。
